# cmd-tech-design-init

## 概要

**AI駆動の技術スタック選定**。会話形式でヒアリング後、Geminiで各技術の2026年最新情報を調査し、Codexで最適な技術構成を検証、`.dgic/steering/tech_stack.md`を作成する。各技術の**選定理由・代替案との比較・リスク評価**を明記し、将来の意思決定やオンボーディングに活用する。

**前提**: `.dgic/steering/product.md`が存在すること（cmd-spec-init 実行済み）

## 実行タイミング

- **cmd-spec-init でproduct.md作成後**に実行（推奨）
- tech_stack.md既存時は上書き前に確認
- 実行時に product.md を参照し、プロダクト仕様との整合性を確保
- product.mdなしで実行時は警告を出すが、ユーザー判断で続行可能

---

## 実行フロー

### Phase 1: product.md 確認

`.dgic/steering/product.md` の存在確認。不在時は警告（続行は可能）。

存在する場合、以下を抽出:
- プロジェクト概要・目的
- ターゲットユーザー・規模
- 制約条件（技術・予算・期間・人員）
- 品質要件（パフォーマンス・セキュリティ等）

---

### Phase 2: ヒアリング

会話形式で自然に情報収集（形式的チェックリスト回避）。

**必須確認事項（3項目）**
1. プロジェクト概要（product.mdなければ詳細ヒアリング）
2. 技術的制約・要件（パフォーマンス、セキュリティ、スケーラビリティ）
3. チームスキルセット（経験技術、学習コスト許容度）

**補足確認（必要に応じて）**
- ユーザー規模・将来の拡張、運用方針（CI/CD、監視）、コンプライアンス、既存システム統合

**重要**: 最後に「他に確認すべき点はありますか？」と確認

---

### Phase 3: Gemini 技術調査（サブエージェント）

`references/tech-research-guide.md` に基づき、ユーザーが選定した技術についてGeminiで調査:
- 最新バージョン・EOL・サポート状況（2026年2月時点）
- 大手採用事例・評判・脆弱性（CVE）
- 2026年ベストプラクティス（ツール、セキュリティ、パフォーマンス）
- 代替技術の最新動向・新興技術
- AI統合・LLM対応状況
- 移行・運用リスク（スケーリング、ライセンス変更）

出力: `.dgic/logs/tech-design-init_research_YYYYMMDD.json`

---

### Phase 4: tech_stack.md 作成

ヒアリング + Gemini調査結果をもとに、`.dgic/steering/tech_stack.md`を作成。

---

### Phase 5: Codex 設計相談（サブエージェント）

`references/design-consultation-guide.md` に基づき、Codexで以下を検証:
- 技術スタック構成の妥当性（組み合わせ、バージョン互換性）
- アーキテクチャパターン推奨（モノリス vs マイクロサービス等）
- 代替案との比較（コスト・学習コスト・保守性）
- リスク軽減策（技術的負債、ベンダーロックイン）
- 開発効率化（CI/CD、テスト戦略、コード品質）
- 認知的負債の最小化
- 2026年先進技術統合（AI/LLM、Context Engineering）

出力: `.dgic/logs/tech-design-init_consultation_YYYYMMDD.md`

---

### Phase 6: フィードバックと完成

要改善項目があればユーザーに説明し、tech_stack.md修正を提案。承認された技術でprojectを進める。
---

## tech_stack.md フォーマット

### 必須項目（各技術について）
- **選定理由**: 3-5文で具体的に説明
- **代替案との比較**: 検討した他の選択肢と不採用理由
- **リスク・制約**: 既知の問題、パフォーマンス/ライセンス制約
- **学習コスト**: Low/Medium/High
- **移行時の注意点**: 将来の技術変更時の考慮事項

### 構造例

```markdown
# 技術スタック設計書

## プロジェクト概要
プロジェクト名 / 作成日 / 最終更新

## 技術スタック

### [カテゴリ]（フロントエンド/バックエンド/インフラ等）

#### [技術名]
- バージョン: X.Y.Z
- 選定理由: (3-5文で具体的に)
- 代替案: 他の選択肢と不採用理由
- 機能・役割: 何を担当するか
- リスク: 既知の問題や制約
- 学習コスト: Low/Medium/High
- 移行の注意: 将来変更時の考慮点

## アーキテクチャ
システム構成とコンポーネント連携

## 技術的制約・要件
パフォーマンス/セキュリティ/スケーラビリティ要件

## 開発環境
CI/CD、テスト、監視、コード品質ツール

## 今後の検討事項
将来導入予定の技術、見送った機能
```
