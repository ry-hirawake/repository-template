# cmd-tech-design-init

## 概要

技術スタック選定を支援し、`.dgic/steering/tech_stack.md`を作成する。各技術の**選定理由・代替案との比較・リスク評価**を明記することで、将来の意思決定や新メンバーのオンボーディングに活用できる技術設計書を作成する。

## 前提条件

**このSkillを実行する前に、必ず `.dgic/steering/product.md` を作成してください。**

- product.mdが存在しない場合、まず **cmd-spec-init** を実行してプロダクト仕様を定義する
- 技術選定はプロダクト仕様（目的・ターゲット・制約）に基づいて行うため、product.mdなしでの実行は推奨されない

## 実行タイミング

- **cmd-spec-init でproduct.md作成後**に実行（推奨フロー）
- プロジェクト開始時に1度だけ実行
- tech_stack.md既存時は上書き前に確認
- 実行時に product.md を参照し、プロダクト仕様との整合性を確保

## ヒアリングガイド

会話の流れで自然に情報収集する。形式的なチェックリストは避け、プロジェクトの文脈に応じて深掘りする。

### 必須確認事項（3項目）
1. **プロジェクト概要・目的**: 何を作るのか、なぜ作るのか
2. **技術的制約・要件**: パフォーマンス、セキュリティ、スケーラビリティ等で特に重視する点
3. **チームスキルセット**: 経験のある技術、学習コスト許容度

### 補足確認（必要に応じて）
- ターゲットユーザー規模、利用環境
- 将来の機能拡張、他システム連携の予定
- 運用方針（デプロイ頻度、監視要件、CI/CD）
- コンプライアンス、既存システム統合、予算・期間制約

**重要**: 会話の最後に「他に確認すべき点はありますか？」と尋ね、プロジェクト固有の要件を拾う。


## 出力フォーマット

`.dgic/steering/tech_stack.md` を以下の構造で作成する。

### 必須記載項目
各技術について以下を明記（これがこのSkillの核心価値）：
- **選定理由**: 3-5文で具体的に説明
- **代替案との比較**: 検討した他の選択肢と不採用理由
- **リスク・制約**: 既知の問題、パフォーマンス/ライセンス制約
- **学習コスト**: Low/Medium/High
- **移行時の注意点**: 将来の技術変更時の考慮事項

### ドキュメント構造

```markdown

- 最終更新: YYYY-MM-DD

## 技術スタック

### [カテゴリ] (フロントエンド/バックエンド/インフラ等)

#### [技術名]
- **バージョン**: X.Y.Z
- **選定理由**: (3-5文)
- **代替案**: 他の選択肢と不採用理由
- **機能・役割**: 何を担当するか

- **学習コスト**: Low/Medium/High

## アーキテクチャ
システム構成とコンポーネント連携

## 開発環境

## 変更履歴 (オプション)
| 日付 | 変更内容 | 理由 | 担当 |
|------|---------|------|------|
```

### 簡潔な記入例

```markdown
# 技術スタック設計書

## プロジェクト概要
- プロジェクト名: タスク管理API
- 作成日: 2026-02-25

## 技術スタック

### バックエンド

#### Node.js 20 + TypeScript 5.0
- **選定理由**: チーム全員がJavaScriptに精通。TypeScriptで型安全性確保し、保守性向上。非同期I/Oがリアルタイム機能に適合。フロントエンドとコードベース統一で開発効率化。
- **代替案**: Go（高パフォーマンスだがチーム経験なし、学習コスト高）、Python（機械学習連携容易だが今回不要）
- **機能・役割**: REST API提供、ビジネスロジック実行、認証
- **リスク**: CPU集約処理には不向き（画像処理等は別サービス化で対応）
- **学習コスト**: Low
- **移行の注意**: スケール時にマイクロサービス化検討

#### PostgreSQL 15
- **選定理由**: ACID準拠でデータ整合性保証。JSONB型で柔軟性も確保。全文検索機能が豊富。チーム内に経験者2名。
- **代替案**: MySQL（機能面でPostgreSQL優位）、MongoDB（スキーマレスだが複雑なクエリに不向き）
- **機能・役割**: データ永続化、トランザクション管理
- **リスク**: 大規模データ時はパーティショニング必要
- **学習コスト**: Medium
- **移行の注意**: バックアップ戦略の確立必須

### インフラ

#### AWS ECS Fargate
- **選定理由**: チーム経験豊富。マネージドでサーバー管理不要。スケーリング自動化。他AWSサービスとの連携が容易。
- **代替案**: GCP（経験不足）、Kubernetes（運用複雑、チーム規模に過剰）
- **機能・役割**: コンテナ実行環境
- **リスク**: コスト管理必須、ベンダーロックイン
- **学習コスト**: Low
- **移行の注意**: IaC化でマルチクラウド対応余地を残す

## アーキテクチャ
API Gateway → ECS Fargate (Node.js) → RDS PostgreSQL

## 技術的制約
- API応答時間: 200ms以内
- 同時接続: 5000ユーザーまで対応
- セキュリティ: JWT認証、OWASP Top 10対策

## 開発環境
- CI/CD: GitHub Actions
- テスト: Jest (ユニット)、カバレッジ80%目標
- 監視: CloudWatch + Sentry
- コード品質: ESLint + Prettier + TypeScript strict

## 今後の検討
- GraphQL導入（複雑クエリが増えた場合）
- マイクロサービス化（規模拡大時）
```

## 品質チェック (AIが実施)

作成したtech_stack.mdを以下の観点で自動評価：

**必須項目**
- [ ] 各技術の選定理由が3文以上で具体的か
- [ ] 代替案との比較が明確か（なぜ不採用か）
- [ ] リスク評価が現実的か（楽観的すぎないか）

**整合性**
- [ ] product.md と矛盾していないか（存在しない場合は確認不可）
- [ ] チームスキルセットに適合しているか

**完全性**
- [ ] 将来の拡張性が考慮されているか
- [ ] セキュリティ/パフォーマンス要件が明記されているか

**品質基準を満たさない場合**: ユーザーに改善提案を提示し、修正を支援する。

## 運用ガイド

### 実行前の確認

**product.mdの存在確認**:
1. `.dgic/steering/product.md` が存在するか確認
2. 存在しない場合は、ユーザーに以下を通知：
   ```
   ⚠️ プロダクト仕様書（product.md）が見つかりません。
   
   技術スタックの選定には、プロダクトの目的・ターゲット・制約の理解が必要です。
   先に cmd-spec-init を実行してプロダクト仕様を定義することを強く推奨します。
   
   それでも続行しますか？（推奨しません）
   ```
3. ユーザーが続行を選択した場合のみ、product.mdなしで実行
4. product.mdが存在する場合は、内容を参照して技術選定の判断材料とする

### 他Skillからの参照
- 実装時は必ずtech_stack.mdを参照し、技術選定と整合させる
- 設計から逸脱する場合は理由を明記

### 更新時
- 技術変更時はtech_stack.md内の「変更履歴」に記録
- 理由・影響範囲・移行手順を明記

### AI活用
- 技術選定の提案: Codex/Geminiで最新動向調査
- レビュー: Claudeで選定理由の妥当性検証
- ドキュメント生成: 初稿作成の自動化
