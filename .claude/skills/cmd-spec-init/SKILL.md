# cmd-spec-init

## 概要

プロダクト仕様を定義し、`.dgic/steering/product.md`を作成する。**何を作るのか・なぜ作るのか・どんな価値を提供するのか**を明確化することで、チーム全体の共通理解を形成し、以降の技術選定・実装・評価の指針とする。

## 実行タイミング

- プロジェクト開始時に1度だけ実行
- product.md既存時は上書き前に確認
- 作成後は cmd-tech-design-init で技術スタック選定を行う

## ヒアリングガイド

会話の流れで自然に情報収集する。形式的なチェックリストは避け、プロジェクトの本質を引き出す対話を心がける。

### 必須確認事項（5項目）
1. **システム概要・目的**: 何を作るのか、なぜ作るのか、どんな課題を解決するのか
2. **ターゲットユーザー**: 誰が使うのか、ユーザー規模、利用シーン
3. **完成形のビジョン**: 最終的にどうなっていれば成功か、理想の姿
4. **成功の指標**: どうやって成功を測るか（KPI、メトリクス）
5. **制約条件**: 技術的制約、予算、期間、人的リソース

### 補足確認（必要に応じて）
- 競合・類似システムとの差別化ポイント
- 特に重視する品質（パフォーマンス、セキュリティ、UX等）
- 懸念事項・リスク（技術的難易度、市場リスク等）
- 将来の拡張計画（機能追加、スケール、連携）
- 避けたいこと（過度な複雑さ、技術的負債等）

**重要**: 会話の最後に「他に定義すべき点はありますか？」と尋ね、プロジェクト固有の要件を拾う



## 出力フォーマット

`.dgic/steering/product.md` を以下の構造で作成する。

### 必須記載項目
- **明確な目的**: なぜこのシステムを作るのか（課題・背景）
- **具体的なターゲット**: 誰が・いつ・どこで使うのか
- **成功の定義**: 何をもって成功とするか（定量的指標）
- **差別化ポイント**: 競合と比べて何が違うのか
- **制約の明示**: 技術的・組織的・時間的制約

### 簡潔な記入例

```markdown
# プロダクト仕様書

## プロジェクト概要
- プロジェクト名: チーム向けタスク管理SaaS
- 作成日: 2026-02-25

## システムの目的
### 解決する課題
小規模チーム（5-20人）がスプレッドシートでタスク管理しており、更新の重複・優先度不明確・進捗可視化困難という課題がある。

### 提供する価値
リアルタイム同期・優先度の自動整理・進捗可視化により、チームの生産性を20%向上させる。

## ターゲットユーザー
### ペルソナ
- 主要ユーザー: スタートアップのプロジェクトマネージャー（25-40歳）
- 利用シーン: 毎朝の朝会でタスク確認、1日数回の進捗更新
- ユーザー規模: 初年度100チーム（500ユーザー）、3年後1000チーム

### ユーザーニーズ
1. 誰が何をやっているか一目で把握したい
2. タスクの優先度を自動で整理してほしい
3. スマホからも簡単に更新できる

## 完成形のビジョン
### MVP
タスク登録・割当・ステータス管理・シンプルなボード表示（3ヶ月）

### 理想の完成形
AI優先度提案・Slack/Teams連携・分析ダッシュボード・モバイルアプリ（1年）

## 成功指標（KPI）
- MAU（月間アクティブユーザー）: 6ヶ月後300人
- 継続率: 3ヶ月後80%維持
- NPS（推奨度）: 50以上

## 差別化ポイント
### 競合・類似システム
- Trello: シンプルだが優先度管理が弱い
- Asana: 高機能だが小規模チームには過剰で高価

### 本システムの強み
小規模チーム特化、AI優先度提案、低価格（月500円/人）

## 制約条件
- 技術的制約: 既存のG Suiteと連携必須
- 予算・期間: 開発予算500万円、MVP 3ヶ月
- 人的リソース: エンジニア2名（フルスタック）
- その他制約: GDPR準拠必須（欧州展開予定のため）

## 品質要件
- パフォーマンス: ページロード2秒以内
- セキュリティ: OAuth 2.0認証、データ暗号化
- ユーザビリティ: 初回利用で5分以内にタスク登録可能
- 可用性: 稼働率99%以上

## リスク・懸念事項
- 競合大手の価格引き下げ（確率: 中、影響: 大）→ 差別化機能で対応
- AI機能の精度不足（確率: 中、影響: 中）→ 段階的改善、手動調整も可能に
- GDPR対応コスト超過（確率: 低、影響: 大）→ 専門家レビュー実施

## 将来の展望
### フェーズ2以降の計画
- AI優先度提案機能（6ヶ月後）
- Slack/Teams連携（9ヶ月後）
- モバイルアプリ（1年後）

### スケーリング戦略
マイクロサービス化、CDN活用、データベースシャーディング

### 他システム連携
GitHub Issues、Jira、Notion との双方向同期

## 避けるべきこと
- 過度な機能追加（シンプルさが強みなので最小限に）
- 大企業向け機能（ターゲット外なのでリソース浪費）
- レガシーブラウザ対応（モダン環境前提でコスト削減）
```

## 品質チェック（AIが実施）

作成したproduct.mdを以下の観点で自動評価：

**明確性**
- [ ] 目的が具体的か（抽象的すぎないか）
- [ ] ターゲットユーザーが明確か（曖昧な表現がないか）
- [ ] 成功指標が測定可能か（定量化されているか）

**実現可能性**
- [ ] 制約条件が現実的か（楽観的すぎないか）
- [ ] リソース（予算・期間・人員）と目標が整合しているか

**完全性**
- [ ] 差別化ポイントが明確か（なぜ使われるのか）
- [ ] リスクと対策が検討されているか
- [ ] 将来の展望が描かれているか（短期的視点に偏っていないか）

**品質基準を満たさない場合**: ユーザーに改善提案を提示し、修正を支援する。

## 運用ガイド

### cmd-tech-design-init との連携
- product.md作成後、cmd-tech-design-init で技術選定を実施
- tech_stack.mdはproduct.mdの内容と整合すること

### 更新時
- プロダクト仕様変更時はproduct.md内の「変更履歴」に記録
- 理由・影響範囲・対応方針を明記

### AI活用
- 競合調査: Geminiで最新の市場動向・類似製品をリサーチ
- ユーザーペルソナ作成: Claudeでペルソナ詳細化を支援
- KPI設定: Codexで適切な指標・目標値を提案
