# cmd-spec-init

## 概要

**AI駆動のプロダクト仕様定義**。会話形式でヒアリング後、Geminiで市場調査・競合分析、Codexで仕様の妥当性検証を実施し、`.dgic/steering/product.md`を作成する。**何を作るのか・なぜ作るのか・どんな価値を提供するのか**を明確化し、チーム全体の共通理解を形成する。

## 実行タイミング

- プロジェクト開始時に実行（cmd-tech-design-init の前提条件）
- product.md既存時は上書き前に確認
- 作成後は cmd-tech-design-init で技術スタック選定を行う

---

## 実行フロー

### Phase 1: ヒアリング

会話の流れで自然に情報収集（形式的チェックリスト回避）。

**必須確認事項（5項目）**
1. システム概要・目的（何を作るのか、なぜ作るのか、課題）
2. ターゲットユーザー（誰が、ユーザー規模、利用シーン）
3. 完成形のビジョン（最終的な理想の姿）
4. 成功の指標（KPI、測定方法）
5. 制約条件（技術、予算、期間、人員）

**補足確認（必要に応じて）**
- 競合・差別化ポイント、品質重視項目、懸念事項、将来の拡張計画

**重要**: 最後に「他に定義すべき点はありますか？」と確認

---

### Phase 2: Gemini 市場調査（サブエージェント）

`references/market-research-guide.md` に基づき、Geminiで以下を調査:
- 競合・類似プロダクト分析（3-5件）
- 成功/失敗事例（各2件以上）
- 市場機会評価（TAM/SAM/SOM、参入障壁）
- リスク評価（市場・技術・規制）
- 推奨事項（実現可能性5段階、差別化妥当性）

出力: `.dgic/logs/spec-init_market_research_YYYYMMDD.json`

---

### Phase 3: product.md 作成

ヒアリング + Gemini調査結果をもとに、`.dgic/steering/product.md`を作成。

---

### Phase 4: Codex 妥当性検証（サブエージェント）

`references/validation-guide.md` に基づき、Codexで以下を検証:
- 実現可能性（技術的難易度、制約との整合性）
- 論理的整合性（目的 vs KPI、ターゲット vs 価値）
- スコープの適切性（MVP、優先度付け）
- リスク分析の網羅性
- 認知的負債チェック（曖昧表現、測定不可能な指標）

出力: `.dgic/logs/spec-init_validation_YYYYMMDD.md`

---

### Phase 5: フィードバックと完成

重大な問題があればユーザーに通知し、修正。改善推奨があれば提示。

## product.md フォーマット

### 必須項目
- **明確な目的**: なぜこのシステムを作るのか
- **具体的なターゲット**: 誰が・いつ・どこで使うのか
- **成功の定義**: 何をもって成功とするか（定量的）
- **差別化ポイント**: 競合と何が違うのか
- **制約の明示**: 技術的・組織的・時間的制約

### 構造例

```markdown
# プロダクト仕様書

## プロジェクト概要
プロジェクト名 / 作成日 / 最終更新

## システムの目的
### 解決する課題
[具体的な課題]

### 提供する価値
[改善内容]

## ターゲットユーザー
### ペルソナ
主要ユーザー / 利用シーン / ユーザー規模

### ユーザーニーズ
[優先度の高いニーズ]

## 完成形のビジョン
### MVP（最小実用版）
[最初にリリースする範囲]

### 理想の完成形
[最終的な成功の姿]

## 成功指標（KPI）
- 指標1: 目標値と測定方法
- 指標2: 目標値と測定方法

## 差別化ポイント
### 競合・類似システム
[既存の解決策]

### 本システムの強み
[競合優位性]

## 制約条件
技術的制約 / 予算・期間 / 人的リソース / その他

## 品質要件
パフォーマンス / セキュリティ / ユーザビリティ / 可用性

## リスク・懸念事項
- リスク1: 発生確率・影響度・対策
- リスク2: 発生確率・影響度・対策

## 将来の展望
フェーズ2以降の計画 / スケーリング戦略 / 他システム連携

## 避けるべきこと
- パターン1（理由）
- パターン2（理由）
```

## 特徴

- 🤖 **AI駆動の検証**: Gemini市場調査 + Codex妥当性検証で客観的評価
- 📊 **2026年最新データ**: 競合分析・市場機会を最新情報で評価
- 🔍 **深い推論**: Codexが論理的整合性・実現可能性を検証
- 📝 **トレーサビリティ**: 調査・検証ログを`.dgic/logs/`保存
- 🎯 **Spec-Driven Development**: 以降の技術選定・実装の基盤

|--------|------|

| **Codex失敗** | 検証なしで継続、手動レビュー推奨 |
| **両方失敗** | ヒアリング結果のみでproduct.md作成 |
